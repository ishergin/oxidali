# Экран: Firmware

Обновление прошивки по URL (`#/firmware`): экран запускает обновление и дальше только
наблюдает.

**Границы:** контракт — [`../rest-api/resources/firmware.md`](../rest-api/resources/firmware.md);
карточка — `web/design-system/screens/firmware.html`.

- **Running image** — слот, из которого исполняется образ (моно). Если сборка не может
  обновиться сама (`ota_capable: false`), строка «Network update: unavailable»
  объясняет, что второго слота нет и путь один — по проводу; формы обновления тогда нет.
- **Плашка «образ ещё не сохранён»** при `pending_verify` — пока образ не доказал себя
  (контракт, §Ход обновления).
- **Update from a URL** — поле URL с черновиком (опрос не стирает набранное) и
  кнопка «Update» («Retry» после отказа). Клиент заранее проверяет схему `http(s)://` и
  предел 96 символов и называет проблему под полем, а не отдаёт её серверу. Во время
  обновления поле и кнопка заблокированы.
- **Прогресс** — состояние, процент (только если сервер прислал длину) и байты, с
  подсказкой: фоновый опрос шины приостановлен, контроллер перезагрузится сам и на
  несколько секунд пропадёт из сети. Пока обновление идёт, экран опрашивает раз в
  секунду, иначе раз в две: полоса, шагающая раз в 2 с, выглядит зависшей.
- **Исход читается из состояния, а не из операции** (контракт, §Ход обновления):
  `operation_id` из `202` экран не отслеживает. Признак успеха — сменившийся слот и
  затем снятый `pending_verify`.
- **Отказ** — карточка «Last update» с кодом шага (`fetch_failed`, `write_failed`,
  `invalid_image`, …) и объяснением в терминах оператора: что не удалось и что при этом
  осталось нетронутым.
