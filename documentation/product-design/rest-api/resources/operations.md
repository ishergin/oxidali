# Ресурс: Operations

Чтение состояния долгих операций — всего, что маршрут принял ответом `202` +
`operation_id`.

## Маршруты

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/v1/operations` | `{"operations": [<operation_id>…]}` — только ключи, без фильтров и пагинации |
| `GET` | `/api/v1/operations/{operation_id}` | `OperationView` или `404 not_found` |

Оба читают одну ограниченную таблицу трекера. Живой поток переходов — канал WebSocket
`operations`, в той же форме.

## `OperationView`

- `operation_id` — строковый ключ (`pd-attr-0-17-42`, `firmware-update`, …), `type`,
  `status`.
- В терминальном статусе — `error {code, message}` при отказе; `result` для apply,
  commissioning и HA discovery (`entities_published` / `entities_failed`);
  `attribute_read_outcomes` для чтения атрибутов. Поля есть только когда применимы;
  вариант `result` различается набором ключей.
- `result` apply групп и сцен — точные итоги по ячейкам (запрограммировано,
  пропущено, отказало и т. п.); `result` каждой процедуры commissioning — в
  [`commissioning.md`](commissioning.md).

## Жизненный цикл

- `accepted` → `running` (владелец начал работу) → `succeeded` / `failed`.
- `succeeded` не значит, что реестр уже спроецировал результат: терминальный сигнал
  трекера и проекция в реестр — разные подписчики шины, и последний исход применения
  групп или сцен может дойти до реестра позже сигнала. Клиент перечитывает ресурс
  (`applied`), пока результат не появится, а не читает его один раз.
- `timed_out` — терминального сигнала не было за TTL операции. TTL зависит от типа
  работы: по умолчанию 10 мин, discovery — выведен из худшего числа кадров скана,
  `config_write` — 10 с (это обход реестра, а не прогон DALI), `firmware_update` —
  5 мин.
- `accepted` → `failed` с `commands_ingress_overload` — команда операции не была
  доставлена владельцу. Это немедленный отказ, а не таймаут: имеет смысл повторить.
- `cancelled` — только автоматическая отмена: операцию вытеснила новая того же типа на
  том же адаптере (кроме `config_write`, который называет ресурс, а не адаптер), либо
  сброс реестра. Публичной отмены нет.
- Завершённая операция хранится 60 с, затем `GET` отвечает `404`. Клиент различает
  «ещё не видна» (сразу после `202`, продолжать опрос) и «уже вытеснена из таблицы».
- `firmware_update` при успехе заканчивается перезагрузкой контроллера, и таблица
  операций не переживает её: исход обновления читается из
  [`firmware.md`](firmware.md), а не из операции.

## Что операций не создаёт

Target-state, вызов сцены, expert-шаги commissioning и прочие синхронные маршруты:
их исход — ответ на сам запрос. Фоновые чтения поллера тоже не создают строк.
