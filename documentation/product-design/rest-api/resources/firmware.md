# Ресурс: Firmware

Обновление прошивки по сети: контроллер сам скачивает образ по URL, пишет его в
неактивный слот, выбирает этот слот и перезагружается; новый образ сохраняется только
после того, как докажет, что работает.

**Границы:** решение, его причины и модель угроз —
[`ADR-024`](../../../architecture/decisions/ADR-024-ota-over-ethernet.md); разметка флеша
и прошивка по проводу — [`../../../architecture/10-build-release-and-tooling.md`](../../../architecture/10-build-release-and-tooling.md).
BDD — [`system`](../../../../tests/dali2rust-bdd/features/system/).

## Маршруты

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/v1/firmware` | `200` — запущенный образ и обновление в работе |
| `POST` | `/api/v1/firmware/updates` | `202` `firmware_update`, `operation_id` = `firmware-update` |

Отменить начатое обновление через API нельзя.

## `GET /firmware`

- `running_slot` — метка раздела, из которого исполняется образ (`ota_0`, `ota_1`, …).
- `ota_capable` — может ли сборка обновиться сама; `false` у хост-сборки и у таблицы
  разделов без второго слота. UI тогда прячет контрол, а не предлагает заведомо
  проваливающийся.
- `pending_verify` — запущенный образ ещё не признан годным: следующий сброс вернёт
  предыдущий слот.
- `update` — `state`, `url` текущего или последнего обновления, `downloaded_bytes`,
  `total_bytes` (`0`, если сервер не прислал длину), `percent` (нет поля, когда длина
  неизвестна: полоса прогресса с выдуманным знаменателем хуже никакой) и `error`.
  - `state`: `idle` → `downloading` → `finishing` (образ записан, слот проверяется и
    выбирается) → `ready_to_reboot` → перезагрузка; либо `failed`.
  - `error` называет **шаг**, на котором остановилось: `bad_url`, `fetch_failed`
    (сервер отказал, пропал или прислал меньше объявленного — для загрузки ничего не
    выбрано), `no_ota_slot` (некуда писать: второго слота нет, или целевой совпал бы с
    запущенным — его стирание уничтожило бы единственный загружаемый образ), `write_failed` (другой
    слот не изменён), `invalid_image` (скачанное не является образом приложения —
    выбирать его контроллер отказался), `no_memory`, `cancelled`.

## `POST /firmware/updates`

Тело — ровно `{"url": "http(s)://…"}`. Handler только принимает запрос: загрузка и
запись занимают десятки секунд и идут в собственном потоке воркера, а задача httpd
продолжает обслуживать оператора, который смотрит прогресс.

| Ошибка | Когда |
|---|---|
| `400 invalid_body` / `400 missing_url` | Тело не объект / нет строкового `url`. |
| `422 unsupported_field` | Любой ключ кроме `url` (контрольная сумма, версия — не принимаются, а не игнорируются молча). |
| `422 unsupported_scheme` | Схема не `http://` и не `https://`. |
| `422 url_too_long` | URL длиннее 96 байт — ширины поля команды; обрезанный URL упал бы необъяснимым 404. |
| `409 ota_unsupported` | `ota_capable: false`. |
| `409 update_in_progress` | Идёт другое обновление (состояние не `idle` и не `failed`). |

## Ход обновления

1. Воркер скачивает образ и пишет его в неактивный слот; слот открывается только
   когда сервер ответил, так что недоступный URL не стоит стирания флеша. На время
   записи фоновая работа DALI (поллер, HCL) приостанавливается; команды оператора — нет.
2. Образ проверяется при закрытии слота (структура и контрольная сумма, которую
   добавляет сборка) — это защита от обрыва или порчи, **не** от подменённого образа:
   обновление не аутентифицировано и не подписано.
3. Слот выбирается для загрузки, операция отмечается `succeeded`, и через несколько
   секунд контроллер перезагружается — столько, чтобы опрос операции успел увидеть
   успех. После перезагрузки таблицы операций уже нет, поэтому исход клиент читает из
   `GET /firmware`: сменился `running_slot`.
4. Новый образ **доказывает себя**: он признаётся годным только после 30 с
   непрерывного здоровья — сейчас это поднятый Ethernet-линк, так что образ, работающий
   в сети, но сломанный иначе, этот критерий не ловит. Пока образ не доказал себя,
   `pending_verify: true`; не доказавший за 3 мин продолжает работать, но следующий
   сброс вернёт предыдущий слот.

Отказ на шагах 1–2 оставляет запущенный образ и выбор слота нетронутыми; операция
завершается `failed` (`execution_failed`, в `message` — имя шага), `update.state` —
`failed`, и можно повторить.
